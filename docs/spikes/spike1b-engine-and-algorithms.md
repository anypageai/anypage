# Spike 1 第二輪：引擎化、機制演算法、Windows 與 Android

2026-10-24。接續 [spike 1](spike1-one-page-all-timings.md)。這一輪做三件事：把示範程式裡的引擎抽成可重用的 crate，改進求值機制的效率，然後讓 Windows 和 Android 兩個宿主都建立在同一個引擎上。

## 結構

| crate | 內容 |
|---|---|
| `anypage-core` | 計算圖與演算法，不依賴任何平台 |
| `anypage-engine` | 每幀排程、預測喚醒、合成器、頁面提供的 GPU 算子、tile 系統、手勢、量測 |
| `anypage-demo` | 示範頁面，只透過 `Page` 介面和引擎溝通 |
| `apps/desktop` | winit 殼：引擎當 App |
| `apps/android` | Kotlin 原生宿主 + Rust JNI 函式庫：引擎當函式庫，自己的繪製執行緒 |

引擎不知道哪些內容是「動畫」。每幀它只問計算圖：可見的出口格中，最早什麼時候會因為時間而改變（`next_expiry`）。已到期就推進時鐘並繪製；未到期就告訴宿主睡到那一刻；沒有任何時間依賴就無限期睡，直到輸入或其他執行緒的資料喚醒它。

## 機制與演算法

### 沒有靜態與動態之分

每個面板都是輸入格的函數，時間是一個輸入格。函數可以宣告自己的值在時間 T 之前有效：

| 函數 | 宣告 | 引擎的反應 |
|---|---|---|
| 連續動畫 | 不宣告 | 可見時每幀求值 |
| 時鐘、游標閃爍 | `valid_until(下一次變化)` | 睡到那一刻 |
| 暫停的動畫 | `valid_until(∞)` | 變回常數，0 fps |

### 求值器的改進

| 改進 | 做法 |
|---|---|
| 提早截斷 | 每個格記下計算時讀到的輸入版本；被標髒後先驗證，輸入沒變就不跑算子。算子可宣告值相等（`op_memo`），算出相同值時版本不變，下游驗證通過 |
| 計時器堆積 | 讀時鐘的格依到期時間放進最小堆積；推進時鐘只彈出到期的格，成本與到期數成正比，與讀時鐘的格總數無關 |
| 分幀求值 | `demand_until(deadline)` 做不完就保存遍歷堆疊，下一幀若圖沒被改過就從原處繼續 |
| 非同步任務不誤殺 | 標髒時不取消任務，驗證確定輸入真的變了才取消重跑 |
| 無配置驗證 | 驗證時直接比對版本，不建立暫存陣列；輸入清單改為共享的 `Arc<[CellId]>` |
| tile 佇列 | 取用改為 O(1)；內容相同的發佈直接跳過 |

### 計算圖基準（`graph_bench`，release，Ryzen 9 5950X）

| 情境 | 結果 |
|---|---|
| 10 萬格，改一個輸入，波及 5,049 格 | 標髒 0.28 ms，重算 2.2 ms |
| 100 萬格，同樣波及 5,049 格 | 標髒 0.32 ms，重算 3.0 ms |
| 提早截斷：輸入變了，截斷點的值沒變，下游 10 萬格 | 只跑 1 次算子，10 萬格免算即確認，共 10.5 ms |
| 可預測時間：1 萬個定時格跑 1 秒（60 次 tick） | 1,429 次算子，不是 60 萬次；每次 tick 0.15 ms |
| 最壞情況：10 萬格長鏈全部重算 38 ms，每幀預算 4 ms | 9 幀完成，最長一幀 4.6 ms |

改進前後：

| 情境 | 改進前 | 改進後 |
|---|---|---|
| 1 萬個定時格跑 1 秒 | 88 ms，每次 tick 都驗證全部 | 9 ms，只碰到期的格 |
| 10 萬格長鏈分幀 | 33 幀，每幀從頭遍歷 | 9 幀，從上次停下處繼續 |
| 10 萬格提早截斷 | 17.9 ms | 10.5 ms |

## Android 結果

Android 15 模擬器（x86_64，AVD `flutter_emulator`），Kotlin 宿主 + Rust JNI 函式庫。模擬器把 Vulkan 轉到主機的 RTX 3090 上執行，所以這些數字代表「同一份引擎在 Android 上正確運作」，**不代表手機效能**。

| 項目 | 結果 |
|---|---|
| GPU 後端 | Vulkan（依序嘗試 Vulkan、GL ES） |
| 字型 | 系統的 Noto Sans CJK（CFF2 可變字型），經 swash 正常顯示中文 |
| 動畫進行中 | 58 fps，App CPU 71%（模擬器負擔） |
| 關掉串流、連續動畫、定時內容後 | **App CPU 0.0%，2 秒內累計 CPU 時間不增加**，所有執行緒睡眠 |
| 操作到上屏 | 點按 p50 31 ms，拖曳 p50 11.9 ms |
| 記憶體 | 動畫中 160 MB，靜止後 66 MB |
| 安裝檔 | APK 14.7 MB，含 arm64 與 x86_64；每個架構的引擎函式庫 strip 後約 7 MB |
| 已驗證的觸控 | 點按按鈕、單指拖曳平移 |
| 未驗證 | 雙指縮放（adb 無法注入多點觸控，需真機）、背景切換時的 surface 重建 |

宿主的分工照架構第 14.4 節：Kotlin 的 `MainActivity` 與 `EngineView` 只負責視窗、生命週期與轉送觸控；引擎在自己的繪製執行緒上，沒有工作時阻塞在通道上，有預測的變化時用逾時精確醒來。`surfaceDestroyed` 會等繪製執行緒放開 surface 才返回。

## 這一輪修掉的問題

| 問題 | 原因 | 修法 |
|---|---|---|
| Android 上所有文字消失 | Android 15 的 Noto Sans CJK 是 CFF2 可變字型，fontdue 不支援 | 字形光柵改用 swash（架構原本就規劃 swash）；Windows 記憶體也從 353 MB 降到 185 MB |
| 視窗被系統要求重繪時無限重送 | 引擎判斷「沒變化」就不呈現，Windows 一直重發 WM_PAINT | 殼分辨重繪是否由自己要求，系統要求的強制呈現一次 |
| 預測變化前可能空轉 | 下個變化在 8 ms 內就要求連續繪製 | 只有已到期才連續，其餘交給精確喚醒 |
| 量測失真 | 游標閃爍造成的重繪被算成串流延遲；刻意的睡眠被算成幀間隔 | 只在串流真的帶來新資料時計延遲；只量連續繪製中的幀間隔 |

## 還沒做或和架構不一致

- 2D 光柵仍用 tiny-skia，不是 vello_cpu；換行是自寫的貪婪演算法，不是 parley。
- wgpu 26，上游已到 30。
- 圖層仍是一個面板一張 texture，還不是從依賴關係自動導出的分層。
- Android 尚未疊原生輸入框（spike 4），也還沒上真機量效能；模擬器的 GPU 是轉到主機 RTX 3090 上跑的，數字不代表手機。
- iOS、macOS、Linux、Web 尚未建置。
